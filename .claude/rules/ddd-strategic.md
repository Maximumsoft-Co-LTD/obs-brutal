# Rule: DDD strategic by default

For every task that involves the **strategic** half of Domain-Driven Design — deciding *where* a model lives and *what language* it speaks, not just *how* its code is layered — invoke the `ddd-strategic` skill **before** drawing boundaries, naming concepts that live in multiple places, integrating with another team's system, deciding investment level in a subdomain, sizing an aggregate, running a discovery workshop, or diagnosing a model that has gone wrong.

This rule is the always-on pointer. The 6 principles (classify the subdomain → discover boundaries from events → one ubiquitous language per context → name the context relationship deliberately → size aggregates around invariants → separate domain events from integration events), pre-flight checklist, failure-mode diagnostics, "below the principles" operational concerns, and the deep-dive guides on subdomain classification, bounded contexts, event storming, and aggregate design all live in the skill:

- `.claude/skills/ddd-strategic/SKILL.md`

**Why:** Most "we need to split this service" or "this codebase has become unintelligible" stories are not architecture problems and not code-quality problems — they are model problems, and the strategic half of DDD is what catches them. A `Customer` class with thirty fields, half nullable, is a model trying to serve two contexts at once. A team that calls the same thing `record`, `row`, `entity`, `account`, and `user` across four files is leaking the translation tax forever. A team that builds a custom CRM, custom auth, and custom invoicing in-house is spending core-domain engineering effort on subdomains that should have been bought. A team that ships microservices drawn around technologies gets every downside of microservices and none of the boundary benefit. Each of these is the same missed fundamental: the strategic decisions about *where* the model lives, *what language* it speaks per place, *how* it relates to other places, and *which* parts deserve full investment versus a CRUD adapter or an off-the-shelf tool. Catching these at design time costs hours; catching them in production costs quarters of rewrite time and lost engineering capacity.

**How to apply:** At the start of any strategic-DDD task, load the `ddd-strategic` skill and run the 6-principle pre-flight (subdomain classification → discovery → language → context relationship → aggregate sizing → domain vs integration events). Apply the relevant reference file when the work is concentrated in one area (deciding what to build vs buy → `references/subdomain-classification.md`; designing or refactoring bounded contexts → `references/bounded-contexts.md`; running a discovery session → `references/event-storming.md`; sizing or splitting aggregates → `references/aggregate-design.md`). The skill itself lists when to skip (generic CRUD, throwaway prototypes, single-context features with no cross-boundary concerns, pure code-level work, pure architecture-operational decisions, no access to domain experts) — defer to it rather than re-deciding here.

**Relation to other skills:** DDD-strategic sits at the *model and language* layer — above any one service's code structure, below any one service's persistence and transport mechanics. It composes with [[programming-fundamentals]] (the code inside an aggregate or value object: illegal-state elimination, pure core, error handling), [[database-fundamentals]] (one bounded context's persistence — the aggregate-as-transactional-boundary is the bridge), [[hexagonal-backend]] (within one bounded context, how the code is layered — aggregates live in the domain layer, repositories are ports), [[architecture-fundamentals]] (the operational mechanics of components on either side of a boundary — this skill decides *what the boundary means*, that one decides *how the boundary survives failure*), [[queue-fundamentals]] (the mechanics of one event channel — this skill draws the line between internal domain events and cross-context integration events; queue-fundamentals operates whichever one crosses a broker), and [[debug-fundamentals]] (the recovery sibling when a bug crosses contexts — debug-fundamentals finds the cause, this skill names the structural fix).

Run order when multiple apply for **construction** work: `ddd-strategic` *first* (where does the model live, what language does it speak, where are the boundaries) → `programming-fundamentals` (the code inside) → `database-fundamentals` (persistence of that code) → `hexagonal-backend` (layering of one context's code) → `architecture-fundamentals` (how components on either side of a boundary relate operationally) → `queue-fundamentals` (the mechanics of any async channel). The intuition: decide the model and language first, then build what was decided.

Run order when multiple apply for **debugging** work: `debug-fundamentals` first (to find the cause), then the layer-appropriate skill — if the cause is a missing language, leaky context, oversized aggregate, or mis-named integration event, that's where this skill applies.

**Status:** Active. Applies to all strategic-DDD work in this project and any project that adopts this foundation.
