# Rule: Architecture fundamentals by default

For every task that involves system-level architectural work — designing a new system, splitting or merging services, adding a new cross-component call, designing an API or event schema, planning failure modes, sizing for scale, or making any decision about how multiple services, modules, processes, or teams relate to each other — invoke the `architecture-fundamentals` skill **before** drawing the first box on a diagram or writing the first cross-boundary call.

This rule is the always-on pointer. The 7 principles (boundaries, single-owner data, sync vs async, resilience, eventual vs strong consistency, observability, contract evolution), pre-flight checklist, "below the principles" operational concerns, and the deep-dive guides on boundaries, communication, resilience, and observability all live in the skill:

- `.claude/skills/architecture-fundamentals/SKILL.md`

**Why:** Most "we need to rewrite this system" stories are not about bad code — they trace back to the same handful of missed architecture fundamentals. Boundaries drawn around technologies instead of bounded contexts so every change requires coordinating two teams. Data owned by no one in particular so two services keep stepping on each other's writes. Sync calls where async would have decoupled time and availability — or async calls where sync would have given the user a real answer. Network calls with no timeout, no breaker, no fallback, so one slow dependency takes the whole platform down. Strong-consistency assumptions silently traded for eventual consistency in the wrong place, or distributed transactions reached for where eventual would have been fine. Systems shipped without observability so the first outage is also the first instrumentation project. API and event schemas treated as private implementation details until the day a "small" change breaks six consumers. Catching these at design time costs minutes; catching them in production costs days of incident time, customer trust, and engineering quarters spent untangling.

**How to apply:** At the start of any system-level architectural task, load the `architecture-fundamentals` skill and run the 7-principle pre-flight (boundaries → ownership → sync/async → failure → consistency → observability → contracts). Apply the relevant reference file when the work is concentrated in one area (designing the shape of the system → `references/boundaries.md`; designing how components talk → `references/communication.md`; designing failure modes → `references/resilience.md`; instrumenting a new component or feature → `references/observability.md`). The skill itself lists when to skip (within-one-service code work, throwaway prototypes, trivial CRUD, pure config edits) — defer to it rather than re-deciding here.

**Relation to other skills:** Architecture fundamentals sit at the *system* layer — above any one service. They compose with [[ddd-strategic]] (decides the *semantic/model* boundary this skill then operates as a runtime boundary — runs **before** this), [[programming-fundamentals]] (code inside any one component), [[database-fundamentals]] (one component's persistence layer), [[hexagonal-backend]] (the internal layering of one service — domain/application/infrastructure), [[queue-fundamentals]] (the mechanics of one queue between two components), and [[debug-fundamentals]] (the recovery sibling, used when a system bug crosses boundaries). They are not competing.

Run order when multiple apply for **construction** work: `ddd-strategic` → `programming-fundamentals` → `database-fundamentals` → `hexagonal-backend` → this skill → `queue-fundamentals`. The intuition: decide where the model lives and what language it speaks, write good code, persist it correctly, organize one service cleanly, decide how that service relates to other services, then handle the mechanics of any async channel between them.

Run order when multiple apply for **debugging** work: `debug-fundamentals` first (to find the cause), then the construction-time skill that owns the fix layer — if the cause is at a system seam (boundary in the wrong place, missing breaker, broken consistency model, lost trace context, breaking contract change), that's where this skill applies.

**Status:** Active. Applies to all system-level architectural work in this project and any project that adopts this foundation.
